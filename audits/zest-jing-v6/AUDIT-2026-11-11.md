## 1. The central claim: a bad `mid` can only make Zest fill less — HOLDS

- In `zest-stage` (L1281–1330) the price bound is `zest-bound limit-price fee sell-stx` (L1296–1299). `mid` enters only as `mid-wad = (/ ZEST_WAD_PRICE mid)` (L1295), which positions the tick walk via `zest-ticks`. The value passed to the pool as the price limit is `bound`, never anything derived from `mid`.
- Entry points assert `limit-price > u0` (ERR_ZERO_LIMIT) and `mid > u0` (ERR_ZERO_MID) at L1340–1341 / L1411–1412 — pre-existing guards, unchanged.
- Adversarial `mid` cases from the source: `mid` huge → `mid-wad` floors to u0 → the `(> mid-wad u0)` guard (L1300) yields an empty tick list → `ZEST_NONE`. `mid` tiny → `mid-wad` up to 1e26 → `zest-tick` clamps to ±4458 → walk sits far from the pool's active bins → pool error or zero fill → `ZEST_NONE` / fall-through to DLMM. `mid` moderately wrong → walk offset from the active bin; the pool still enforces `bound` per bin, so fills are bounded by `limit-price` net of fee, only fewer. I could not construct a `mid` that worsens any fill past the bound.

## 2. `zest-bound` rounding: conservative in both branches

Transcribed exactly (L1236–1245):

- sell-stx=true: `floor(floor(1e26 · (1e8 − fee) / limit) / 1e8)` vs ideal max-price `1e26·(1−fee/1e8)/limit`. Nested floors can only lower the max-price → stricter.
- sell-stx=false: `c = ceil(1e34/limit)`, then `ceil(c/(1e8 − fee))` vs ideal min-price `1e34/(limit·(1e8 − fee))`. Nested ceils can only raise the min-price → stricter.

Exact-arithmetic sweep (`verify_math.py` §1): **63,360 (limit, fee, direction) cases — 0 loosening violations.** Limits covered 1…499 exhaustively, powers of 10 to 1e19, 3,000 randoms to 1e14, and realistic price points; fees {0, 1, 100, 3000, 5000, 9999, 1e6, 5e7, 1e8−1}. This agrees with the fork/exact-arithmetic results in submissions `mwb114r657ac087d6f18` and `mwb33cr164b539598bce`, and refutes Finding 1 of `mwayu2iv42ed53374c25` (whose proposed "ceil for sells of STX" fix would *loosen* the x→y bound).

## 3. Correction: the claimed `zest-bound` uint128 overflow (L1243) is unreachable

Submission `mwb0ac1nd72924dc55af` claims `(+ (* ZEST_WAD_PRICE ZEST_FEE_ONE) (- limit u1))` at L1243 aborts with `ArithmeticOverflow` when `limit > 2^128 − 10^34`, breaking "no fill never reverts" for `smart-swap-usdcx-for-stx`. The arithmetic premise is right; the reachability is not:

1. `zest-bound` has exactly one caller: `zest-stage` (L1297).
2. `zest-stage` evaluates `dust-left left limit sell-stx` **first** (L1287) and returns `ZEST_NONE` when it holds. For sell-stx=false, `dust-left` fails (stage proceeds) only when `limit-min(left, limit) ≥ u2`, i.e. `floor(base · 1e8 / limit) ≥ 2` with `base = left − u2` (ROUND_SLACK, L579), i.e. **`limit ≤ base · 1e8 / 2`**.
3. `base · 1e8` is itself computed inside `limit-min`; for the guard to return at all, `base ≤ (2^128−1)/1e8`, so any `limit` that reaches `zest-bound` satisfies `limit ≤ (2^128−1)/2 ≈ 1.70e38`. The claimed overflow needs `limit > 2^128 − 10^34 ≈ 3.40272e38`. Between the two bounds there is no input: past them, either the stage is dust-skipped, or the abort happens inside the pre-existing `limit-min` multiplication — v5-5 code, exposed identically by `dlmm-stage` in v5-5 — which is not a v6-caused path.
4. Numeric confirmation (`verify_math.py` §3): max reachable addition at L1243 is `170151183460469231731687303715849999999 < 2^128`, roughly a 2× headroom.
5. The sell-stx=true branch needs no such argument: its largest intermediate is `1e26 · 1e8 = 1e34` for every input. Both branches' divisors are safe on every reachable input: `limit ≥ u1` is asserted at entry, and `zest-bound` runs only under the `(< fee ZEST_FEE_ONE)` gate (L1296), so `(− ZEST_FEE_ONE fee)` ≥ u1 and `(− limit u1)` ≥ u0.

So the v6 line can never be the abort site; the "valid swap reverts" scenario does not exist through the Zest stage.

## 4. Tick math: never overestimates, at most 1 low, walk endpoints sound

`zest-log2` (L1148) normalizes x into [2^60, 2^61) (`(log2 x)` built-in + shifts — shift amounts keep the mantissa exact, and `m·m` in `zest-log2-bit` stays below 2^122), then extracts 16 fractional bits by repeated squaring. `zest-tick` (L1167) applies a true mathematical floor for negative numerators (the `(* q ZEST_LOG2_STEP) ≠ num` correction) and clamps to ±4458.

From-source Python reimplementation checked against **true ticks computed by exact big-integer comparison** against bin edges `1e18 · 101^t / 100^t`: **766 vectors** (every bin edge t ∈ [−60, 60] with edge−1/edge/edge+1, 400 random WADs up to 1e27, 1/1e18/1e26/1e27) — **0 overestimates, 0 cases more than 1 low, max deficit exactly 1 tick.** This independently confirms the −1-at-bin-edges behaviour reported as F-01 by `mwaz7eay026a9dbc0c7c` (and by `mwazgoame732c69fddb7`, `mwb0ac1nd72924dc55af`) — prior art, not claimed; the ±2 walk margin absorbs it.

`zest-ticks`/`zest-tick-step` (L1186–1233): the fold appends a contiguous run starting at `tick(mid) ∓ 2`, stops one past the bound's tick (`tb + 1` up / `tb − 1` down), and is hard-capped at 32 by the fixed `ZEST_WALK` list — the `unwrap-panic` on `as-max-len?` is unreachable because the fold runs exactly 32 iterations and appends at most once per iteration. The one-bin overshoot past the bound tick is harmless: the pool enforces the `bound` price argument itself; the extra bin can only be read, never filled past the bound. If start is already past end (limit on the wrong side of `mid`), the list is empty → stage skipped, as the header promises.

## 5. Split swaps: `leg-zest`, the u3004 sum, and the `unsold` identity

- `leg-zest` (L251–289) calls `clmm-router-v1` `swap-x-for-y` / `swap-y-for-x` with the same argument order as `zest-swap` — amount, price, ticks, min, `allow-partial-fill=false`, deadline `stacks-block-time` — and maps the response symmetrically (x→y: in=dx, out=dy; y→x: in=dy, out=dx). The min passed is `(amm-floor (get zest amm-mins))` — the caller's per-leg min, floored to u1, **not** scaled: correct, because unlike DLMM the Zest slice is never resized by fallback (`scale-min` exists for legs whose executed amount can differ from the planned one; the Zest amount is fixed, and the header states Zest is not a fallback venue).
- The u3004 check now sums `jing + dlmm + xyk + velar + zest = amount` in both split entry points (L371–378, L485–492). All five addends are caller-bounded uints; a sum overflow aborts instead of returning u3004 — the same behaviour the 4-way sum had in v5-5, not a v6 regression.
- `unsold` (L427–433, L541–547) is **unchanged** from v5-5 — Jing residual (net of routed fallback) + DLMM shortfall — and stays exact with Zest added: `leg-zest` runs under `try!` with `allow-partial-fill=false`, so on success `zest-in` always equals the planned zest slice; a partial Zest fill reverts the whole split, as does every other leg. The identity therefore needs no zest term. (This is the substance of `mwb0ac1nd72924dc55af` item 3 — prior art, not claimed.)
- Caller-supplied `zest-route {ticks, price}` can only hurt the caller: wrong-direction or out-of-range ticks make the pool revert (whole split aborts, funds unmoved), and a price looser than the caller's intent is still fenced by `amm-mins.zest` and the combined min-out assert. I note `mwb33cr164b539598bce` F-3 (split price never reconciled against a limit) as prior art; within the split design — per-leg mins + one combined min-out, no `limit-price` parameter exists — I find no additional hole.

## 6. Smart swaps: remainder chain, receipts, and the no-revert property

- Remainder chain verified at L1352–1354 and L1423–1425: `dlmm-stage` receives `amount − jing-in − zest-in`; `cp-stage` receives `amount − jing-in − zest-in − dlmm-in`. `unsold` comes from `cp-stage`'s own accounting of that final remainder, so Zest-consumed input is never double-counted as unsold and never re-offered to DLMM. The final assert prices the **balance-measured** `out` (gain of the user's USDCx/STX balance across the whole call) against `min-usdcx-out`/`min-stx-out` (L1357, L1428), so the Zest output counts toward the one combined min-out exactly as the header states.
- Receipt/print: `zest-in`/`zest-out` sit immediately after `jing-out` in both tuples; print additionally carries `zest-ok` (the pool call returned ok) and `zest-ticks`. Field semantics are accurate on every path: stage skipped → 0/0/false/0; pool error → 0/0/false/(len ticks) — `zest-swap` preserves `(len ticks)` in its error merge (L1265, L1276), so `zest-ticks` reports the walk that was attempted, not a fabricated 0.
- No-fill-never-reverts, smart path — every `zest-stage` exit enumerated: dust remainder → `ZEST_NONE` (L1287); `get-fee-rates` error → `ZEST_NONE` (L1310); fee ≥ 1e8 → bound forced to u0 → empty ticks → `ZEST_NONE` (L1296–1303); bound = u0 (extreme limit) or `mid-wad` = u0 (extreme mid) → empty ticks → `ZEST_NONE`; empty walk (limit past market) → `ZEST_NONE`; pool error (paused, no liquidity in the listed bins) → `ok:false, in:0, out:0` with the tx intact (L1265/L1276). A Zest error rolls back only Zest's own writes; Jing's fill and the DLMM/cp stages proceed. On the split path, Zest errors propagate through `try!` — the pre-existing all-or-nothing pattern every leg had in v5-5, which the bounty itself flags as not v6-caused.

## 7. Custody and post-conditions

The router contains **no `as-contract` in code** (the two matches in the file are the header comment explaining exactly this). Both Zest call sites run as the user; Zest's `wstx` transfer is a plain `stx-transfer?` and `clmm-pool-v1` pulls/pays with `tx-sender` as the principal on both sides (per the v6 header's trace of the pool, consistent with the balance-measured `out` in §6: any router custody would show up as a balance discrepancy the min-out assert would catch). No error path strands funds: a reverted split moves nothing; a smart swap's stages only ever move funds user → venue → user. The deny-mode post-condition completeness issue (new paying principal decided on-chain) is `mwb0nok064ffd9086408` F-2 — prior art, not claimed; my source read is consistent with it.

## 8. Cost

The diff adds no unbounded iteration: `zest-ticks` folds a fixed 32-element list, `zest-log2` folds a fixed 16-element list, `zest-stage` adds one `get-fee-rates` call and at most one pool swap. Worst-case added cost is constant-bounded by construction, in line with the poster's measured table (32 ticks + full DLMM walk ≈ 11% of block reads).
